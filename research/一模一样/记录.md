# 「一模一样」档：老师的要求、设计过程、实测、淘汰的做法

## 老师的要求（10-03，原话要点）

- 「在完美之上再做一个……叫一模一样……从刚开始到最后每一个环节都想方设法……做的跟我的声音完全一样」
- 「用尽全力去压榨任何能够使用到的资源和硬件……世界最顶级的质量」
- 「只要我再去从头到尾做我的声音……它会自动直接去跑这个最高档……除非我自己主动要求去换挡」
- 「最大限度的压榨内存、最大限度的压榨显卡……让显卡发挥最大的作用」

我的回答：每个环节都做到能做的最多；**任何声音克隆都做不到百分之百一样**，结果以每句实测的「像你本人（%）」为准，
不写没测过的数字（永久规定 7）。

## 设计过程（多代理工作流，10-03）

1. **摸清现状（2 路）**：素材 → 训练 → 挑模型一路；生成 → 挑选 → 拼接 + 打分一路。逐行读代码，并从官方仓库取了
   GPT-SoVITS 的源码核对（老师用的 api_v2.py 是官方提交 abe9843，和 `tests/gsv_real/api_v2.py` 逐字节一样；
   另一个是 20250606v2pro 标签的版本）。
2. **三个方向各设计一套**：生成时更用力地找（搜索）、素材和模型（训练）、听感和打分（感知）。
3. **两个评审**：核对每条说法是不是和代码、真实 api_v2 一致；一个看技术正确性，一个看风险和对老师说的话是否诚实。
4. **合成最终方案**：`设计方案原文.md`（英文原文，近千行：每个阶段做什么、改哪些代码、参数、界面文字、测试、
   时间估计、开发机上验证不了的东西和老师怎么检查、风险和退路）。全部过程（两份现状图、三套设计、两份评审）在
   `设计过程原文.json`（临时文件夹路径已经去掉）。

## 淘汰的做法（为什么）

- 把生成的声音的频谱「均衡」成老师的样子：违反绝对静音 / 不加处理的永久规定，而且打分本身就是按老师的声音校准的，自己骗自己。
- 按声调检查读错：pypinyin 的声调判断不可靠，会误报。
- 同一篇里每句在 V4（48 kHz）和 v2ProPlus（32 kHz）之间换：频宽不一样，听起来忽亮忽暗，打分（16 kHz）又看不出来。
- 保留句首吸气声、自动重新处理去过杂音的素材、再开一个合成引擎、加大验证集（会减少训练素材）、「显卡一直满负荷」这种没测量的说法：都不做。

### P3：实测你本人的说话习惯（twin_profile.json）和参考录音库（refs_bank.json）——只用处理器

**做了什么**

- 新文件 `voicetwin/style/twin_profile.py`（`TWIN_PROFILE_VERSION = 1`）：
  - `source_gaps(wav, sr)`：10 ms 一帧、40 ms 窗、自动静音阈值、至少 120 ms 的静音（和切片量停顿是同一个方法）；
    `source_gaps_file(path)` 是分块读文件的版本（一次 60 秒），结果和整个读进来一样（测试里逐个比过）。
  - `align_pauses(text, clip_pauses)`：标点位置（前面的音节数 / 全部音节数）和停顿位置（(停顿中点 − 开口) / 开口到收音）
    做 Needleman–Wunsch 动态规划，跳过一边各算 0.08，位置差 ≤ 0.12 才对上；没对上的停顿算「犹豫」。
    数字里的「3.14」「1,000」、缩写「e.g.」不算标点；连着的标点（「？！」）算一个。
  - `acoustic_features` / `clip_features`：开口和收音、片段里面的停顿、发声时长、讲话时的响度、响度起伏（p90 − p10）、
    音调（`prosody.f0_frames`，新加的，带每帧的时间；`f0_track` 的结果一个字节都没变）：中位数、起伏（p90 − p10 半音）、
    整句的下降速度、最后 300 ms 的升降；句首起音 / 句尾收音（2.5 ms 一帧，从底噪到比最响处低 30 dB）；开口前像吸气的声音
    （只记录）；22 个 1/3 倍频程的频谱（先换成 32 kHz，只记录）；去静音（留 80 ms）后的起止样本（参考录音库用）。
  - `build_twin_profile(project)`：写 `workspace/<声音>/twin_profile.json`（先写临时文件再换上去，键排序、没有时间戳，

**和设计不一样的地方（为什么）**

1. 设计里测试声音的「句号停顿中位数在 0.55~0.85 秒」是按字幕时间算的旧方法（profile.json 里的 0.77 秒），少算了每句
   音频自己带的静音（句末停顿 0.45 秒 + 0.08 秒 + 下一句开头 0.05 秒）。真实的数字静音是 1.244 秒，重新量的 1.21 秒；
   测试改成和按同样种子算出来的真实值比（差 ≤ 0.06 秒）。逗号停顿仍按设计在 0.19~0.29 秒（0.20）。
2. 片段后面的停顿按片段最后一个标点的类别归类（不只句号）：片段里面的 + 片段后面的合起来才是这一类的全部停顿，
   只用一部分会偏（切片专挑长停顿切）。最后没有标点的片段，后面的停顿不用（不知道是什么）。
3. 原始录音找不到时，切片记下的「片段后面的停顿」不用（就是要去掉的偏差），所以 `source = clips` 时
   `sentence.n_final = 0`。部分视频有原始录音、部分没有时 `source = mixed`，另记两边各几个视频。
4. signature 里另外加了原始录音文件的大小和修改时间：原始录音删了 / 换了也会重算。
5. `align_pauses` 多返回每类标点各有几个（算 P(停顿|标点) 要用）；`clip_features` 多一个可选的 `f0_ref_hz`
   （算 `f0_med_st` 要先知道你整体的中位数）；声音特征（和文字无关）单独缓存。
6. 校对表保存 / 确认时有上限：要新量的超过 60 段或原始录音超过 50 MB（第一次，还没量过）就这次不量，留到素材准备、
   「重新分析说话风格」、生成「一模一样」（P8）时再量——否则升级后第一次点「保存修改」要多等一分钟左右（估计）。
7. 原始录音分块读：一小时 44.1 kHz 的录音整个读进来算逐帧电平，按数组大小算要 4 GB 以上内存（float64 的平方和累加和）。
8. `build_reference_bank` 不传 judge 时不算声纹（`self_pct`、音色变化是 null）；P8 准备「一模一样」时传精准打分进来
   （没有精准打分时就传现有的退回打分）。去静音的位置按样本存（`trim = [起, 止, 采样率]`），之后写的音频长度和量的完全一样。
   多一个 `progress` 参数（P8 的进度「给你的 n 条录音打分，挑参考录音……」）。`para_initial` 用原始录音上重新量的前面停顿。
9. 分位数除了 p05…p95 再存 p97（P6 段落停顿要用到 u = 0.97）和中位数；停顿只统计 0.12~4 秒（和 profile.py 一样，
   更长的多半是在写板书）。

**淘汰的做法**

- 停顿位置按「只算说话的时间」换算（比设计的公式更贴近音节比例）：按例子算差别 < 0.02（对上的门槛是 0.12），按设计的公式做。
- 保存时在后台线程里量（保存马上返回）：后台还在写缓存时别的操作（复制声音文件夹、同时在跑的任务）会碰到写到一半的文件，可能偶尔出错（没有试，按道理推的）；改成上面的上限，第一次量留到素材准备 / 生成时。

### P4：一次请求同时生成同一句话的好几个版本

**做了什么**

- `voicetwin/backends/base.py`：`supports_batch = False`；`synthesize_many(req, n, out_dir) -> [(文件, 第几个)]`
  通用做法是一个一个生成，第 k 个用种子 `seed + k × 104729`（`SEED_STEP`），编号 0..n-1；文件名带流水号，
  同一个文件夹里多次调用不会互相覆盖（审查后改成「这次运行随机取的一串字 + 流水号」，不同次运行也不会覆盖，见下面）；`release_gpu_callback`（显存不够时先调用它让出显存，由 P5 的生成引擎登记）。
- `voicetwin/backends/gptsovits.py`（`supports_batch = True`）：
  - `synthesize` 拆成 `_payload(req, *, batch=1, interval=0.3, speed=None)`（单独生成的请求一个字段、一个数都不变，
    有测试逐个字段、逐个类型比）+ `_tts_answer`（发请求、认出失败；失败的报错和以前一样，另外带 `oom`：
    **只看这一次请求的原因**，引擎记录里以前的显存不够不算）。
  - `_batch_text(text, lang, n)`：照抄官方的切分规则（`replace_consecutive_punctuation`、`pre_seg_text` 用 cut0、
    `merge_short_text_in_array(…, 5)`、开头加「。」/「.」的规则），算出来正好 n 段、每段和单独生成的一样才返回复制好的文字；
    有换行、超过 400 个字、「好的。」这种会被合在一起读的短句返回 None。`lang` 用 `_payload` 里的 text_lang（P1 改了
    语言规则以后自动跟着变）。
  - `_split_fragments(data, n, interval=0.5)`：先修半精度溢出（`_fix_int16_wrap`），至少 `round(0.6 × interval × 采样率)`
    个连着的 0 才算版本之间的静音，必须正好 n 段、最后一段静音到结尾（差 1 个采样点以内）、每段至少 0.3 秒而且有声音，
    每段后面补 0.3 秒的 0（和单独生成一样）。切不开时 `_split_wav` 另给中文原因。
  - `_speed_trick_ok(req)`：同一个种子 1.0 和 1.0001 各一次（长度差 ≤ 1%、波形相关系数 ≥ 0.99），再同时生成 2 个要能切开；
    最多 2 个种子；每次启动新的引擎重新查（`start()` 里清掉）；结果记在 `batch_stats["speed_trick"]` 和中文日志。
  - `synthesize_many(req, n, out_dir)`：只要 1 个、文字不行、模型不是 v2 / v2Pro / v2ProPlus、语速正好 1.0 而自检没通过时
    一个一个生成；否则一次请求（`batch_size = n`、`fragment_interval = 0.5`、语速 1.0 时发 1.0001）。显存不够：数量减半
    （日志「显存不够：每次同时生成的数量从 a 减到 b，接着试（不会停下）」，记住以后最多同时生成几个）；减到 1 个还不够，
    先调用让出显存的回调、再试一次，还不行就是以前的报错（errors.explain 认作「显存不够」、生成停下）。切不开：日志
    「这次没能把同时生成的几个版本分开（原因：…），改成一个一个生成」，一个一个生成。
  - `batch_stats`：requests、pieces、每种数量的请求数 / 版本数 / 秒数（`by_batch`）、oom_backoffs、split_fallbacks
    （和最后一次的原因）、gpu_releases、一个一个生成的原因和次数、speed_trick、max_batch。`last_many` 记最近一次实际
    怎么生成的（同时生成的数量和种子，或一个一个生成的每个种子）——P5「只改语速再生成一次同一个请求」要用。
- `voicetwin/eval/metrics.py`：`CERChecker.release_gpu()`：卸掉已经加载的 Whisper / Paraformer，以后要用时在处理器上
  重新加载（Whisper 用 int8），再清 PyTorch 的显存缓存（这个程序里没 import 过 torch 就不清；出错不抛出来）。
  识别时拿着一把锁，不会在识别到一半时把模型卸掉。
- `tests/fake_gptsovits.py`（真实 api_v2 用的假 TTS 和模拟版 api 都改了）：文字里有换行时按换行切开（不到 5 个字的和后面的
  合在一起），每段一个不同音高的正弦波（150 + 10 × ((seed + 第几段) % 7) Hz），每段后面补 fragment_interval 秒的 0；
  `FAKE_GSV_MAX_BATCH=N`、`FAKE_GSV_SPEED_TRICK_BROKEN=1`、`FAKE_GSV_INNER_ZERO=1`。一次一个时和以前完全一样。
- 生成引擎还没有用 `synthesize_many`（P5 才用），所有档位现在的行为都没变。

**和设计不一样的地方（为什么）**

1. 判断模型版本用的是**正在用的** SoVITS 模型文件（自动挑选时是正在试的那个），用现有的 `detect_sovits_version` 读；
   读不出来（别处的服务、不认识的版本标记）时按设置里的版本。设计写的 `model_version_info()` 只看「选中的」模型，
   P8 挑选时试 V4 会认错。
2. 显存不够减半以后，这一次只返回减半后那一次请求的几个版本（可能比 n 少），不另外补请求；调用的地方按实际个数算。
   切不开时一个一个生成的个数也是当时的数量。这样每个版本都对应「一次请求 + 第几行」，P5 重发同一个请求只改语速时才对得上。
3. 「让出显存再试一次」对 `synthesize_many` 里所有单独生成的请求都有效（包括一开始就一个一个生成的），不只是减半减到 1 以后。
4. 自检出错（比如显存不够）时不换第二个种子再试（出错不是计算上的小出入），这次按没通过、不记住，下次再查；
   但自检里同时生成 2 个就显存不够时记下「一次一个」，以后不再每句都自检。出错时 `speed_trick` 记 None（没测出来）。
5. `batch_stats` 比设计多几项（gpu_releases、一个一个生成的原因、切不开的原因、max_batch、自检没通过的原因），
   另加 `last_many`：报告和 P5 要用，都是实测的。
6. 让出显存的回调是引擎上的一个属性 `release_gpu_callback`，P5 由生成引擎登记 `CERChecker.release_gpu`。
7. `release_gpu` 是卸掉、以后在处理器上重新加载（faster-whisper 的模型不能直接搬到处理器上）。
8. 模拟引擎：一次一个的请求保持 150 Hz 和原来的时长（以前的测试一个不用改），不同音高只用在同时生成的几段上；
   `FAKE_GSV_INNER_ZERO` 对每一段都有效。测「切不开」和「一个也生成不了」时用语速 0.9，直接走同时生成（不用先自检）。
9. P1（`send_lang`）还不在这个分支上：`_payload` 里的 text_lang 还是原来的规则。合并时 P1 对 synthesize 请求的改动要改在 `_payload` 里。

**留给 P5 的问题**

- 一个一个生成时第 k 个的种子是 `seed + k × 104729`，设计 §1.7 里第 j 次请求的种子也是 `… + j × 104729`：
  如果第 j 次请求切不开、改成一个一个生成，它的第 k 个和第 j + k 次请求（也一个一个生成时）的第 0 个是同一个种子，
  会生成一模一样的版本。P5 编请求的种子时要错开（比如按 B × 104729 往后排）。

**淘汰的做法**

- 显存不够减半后补够 n 个（再发几次请求）：每个版本就对不上「哪一次请求的第几行」，重发同一个请求只改语速时找不到同一行；
  而且 P5 本来就按实际拿到的个数决定还要不要再试。
- 把显存不够做成新的异常类型：报错的类型名会写进详细说明（`errors._one` 写成「类型名: 消息」），说明就和以前不一样了；
  所以还是普通的 RuntimeError，只多一个 `oom` 属性，报错和以前一模一样。

### P4 审查后的修改（两位审查员的 4 条意见，都是真的，都先写了测试、改之前都失败）

1. **自检没做完时，记下的原因写成了「自检没通过」**（意见 1，复现了）：`_single_reason` 只看 `_speed_trick_ok` 返回 False，
   就记「「语速 1.0001」自检没通过（语速正好 1.0 的句子）」。可它返回 False 有三种情况：真的没通过（记住了）、
   自检时出错没做完（`_speed_trick` 还是 None）、自检里同时生成 2 个就显存不够（`_max_batch` 变成 1）。日志写对了
   （「自检没做成」），`batch_stats["single_reasons"]`（P6 总结里「这次没能用上……（原因：…）」要显示的）写错了。
   复现：同时生成 2 个就显存不够、语速 1.0、要 3 个 → 记的是「自检没通过」，其实是显存不够。
   **改法**：自检之后看情况——`_max_batch ≤ 1` 记「显存不够，已经改成一次生成一个」；`_speed_trick` 是 None 记
   「「语速 1.0001」自检没做成（自检时出错：……）」；只有真的做完没通过才记「没通过」。
2. **文件名的流水号每次运行都从 1 数起**（意见 2，复现了：两个进程先后写进同一个文件夹，第二次的 `many1_r0.wav`
   覆盖了第一次的）：说明里写的「同一个文件夹里多次调用不会重名」只在一次运行里成立。现在还没有地方调用
   `synthesize_many`（P5 写进临时文件夹、留下来的候选另存成 `c{k}.flac`），但说明和记录写的是做不到的事。
   **改法**：`base.many_prefix(out_dir)`：文件名开头是「many + 这次运行随机取的 8 位十六进制 + - + 流水号」，
   万一文件夹里已经有这个开头的文件就换下一个流水号；通用做法、GPT-SoVITS 一个一个生成、同时生成三处都用它。
   淘汰：用 `tempfile.mkstemp` 先占住文件（三处写法不一样：单独生成是 synthesize 自己写、同时生成是切开后写，
   要改的地方多）；只把说明改成「一次运行里」（P5 以后再改，容易忘）。
3. **没让出显存也记了一次「让出显存」**（意见 3，复现了）：一次一个也显存不够时，不管有没有登记回调、回调有没有卸掉模型，
   `gpu_releases` 都加 1，日志也在回调运行之前就说「先让出显存（识别校验模型改到处理器上运行）」。
   **改法**：回调返回真值（`CERChecker.release_gpu` 卸掉了模型时返回 True）才记 `gpu_releases`；日志在回调之后按实际写：
   「已经让出了一部分显存，再试一次……」/「没有能让出的显存，再试一次……」/「没能让出显存（原因），再试一次……」/
   没登记回调时只写「再试一次……」。不管让没让出都照旧再试一次，还不行才报「显存不够」。
4. **自检通过的日志说了没量过的事**（意见 4，复现了：1.0001 长 0.89%、加了噪声、相关系数 0.9902 的回答也显示
   「引擎每个版本单独解码，声音和 1.0 一样」）：自检只量了长度差、波形相关系数和 2 个版本能不能切开。
   **改法**：`_speed_trick_once` 把量出来的长度差和相关系数也返回，日志改成「自检通过：语速写成 1.0001 和 1.0 生成的声音
   几乎一样（长度差 0.01%、波形相关系数 0.999），同时生成的 2 个版本也能按数字静音分开——可以同时生成好几个版本」；
   相关系数往下舍到 3 位（0.9996 写 0.999，不会写成 1.000 让人以为完全一样）。

**和设计不一样的地方（为什么）**

1. 种子：第 j 次请求 = 基础种子 + 第几句 × 7919 + j × B0 × 104729（B0 = 这种显卡每次最多同时生成几个），不是 j × 104729：
   切不开改成一个一个生成时，第 k 个用 +k × 104729，按设计的写法会和第 j + k 次请求的第 0 个撞上同一个种子（P4 记录里留下的问题）。
   没有 N 卡（B0 = 1）时和设计完全一样。
2. 「像你本人」那一项：先封顶再减差别，2.0 × (min(平均, p90) − 0.5 × 差别) / 100；设计写的是 2.0 × min(平均 − 0.5 × 差别, p90) / 100。
   设计自己的测试（130% / 差别 20 要排在 105% / 差别 2 后面，封顶在 p90）按设计的公式只要 p90 ≥ 104 就做不到；而且按设计的公式，分数一过封顶，
   几个模型说法差多少就不再起作用。lcb 字段还是存「平均 − 0.5 × 差别」。
3. 留下来的版本存在 pool_key（缓存键去掉排序权重的版本）下面：设计把权重版本放进了缓存键，又要求权重变了时不用显卡重新排——两个都要做到，
   就得让留下来的版本不跟着权重变。说话习惯 / 打分标准变了不改缓存键，靠记录里的 profile_sig / judge 发现。
4. 留下来的是引擎原样的声音（还没去首尾）：重新排名时和当时打分用的是同一段声音，分数一个数都不差（FLAC 16 位读回来一样，实测）。
5. quick / full 收的是文字和发给引擎的语言（不是整个句子对象），测试时好造。
6. 停下的规则在每一轮结束时、第 3 轮每次请求以后查（第 1 轮每种组合都先试完）；「最近 8 个没再高 0.02」= 全部里最好的 −
   去掉最近 8 个新版本以后最好的，比的时候把「读对了 / 达标」的档次也算上（档次变高算变好）。
7. 两步打分：先保证每种组合最好的那个、再快速分前 12 名，并给还没出场的组合（第 1 轮的、可能加的 3 种）留名额——不然前几种组合就把
   24 个名额用完了（按一直变好的分数算一遍：第 4 种组合出场时 24 个已经用完）。语速微调的版本一定完整打分、不占 24 个的名额；也不算在「试了几个」里
   （小结写「最多 64 个」时不会出现 66 个），另记在 search.refine_requests / refined。
8. 请求的大小：一共不超过每句最多试几个；第 1 轮给后面每种组合至少留 1 个（命令行 -n 很小时也每种组合都试到）。
9. 参考录音库：生成「一模一样」时库还没有、或者是这里（不带声纹）建的，就重新整理一遍（几毫秒到一两秒）；带声纹的库（P8 建）不动，
   只用里面现在还能用的录音（片段还在、还用来训练、文字没改过），指纹按这些录音算。一条可用的都没有时用 references.json（指纹 "refs:…"）。
10. 已经有版本、后面连着 4 次请求什么都没拿到时停下用已有的（设计只写了「一个版本都没有」时放弃）。
11. 音调起伏 / 频谱形状只在权重不是 0 时算（默认 0；每个完整打分的版本省约 45 毫秒）。
12. `check_mixed` 多返回 errors_cjk / errors_en / hyp_en；给老师看的识别结果 = Paraformer 的字 +「（英文：…）」。
13. 两个模型都留着时的第二遍（pass B）没做：要等 P8 在 models.json 里写 identical.ckpts。
14. 显卡打分只对精准声纹模型（全是 ONNX）做；空闲显存用 nvidia-smi（utils.gpu._query_smi）量。

**淘汰的做法**

- 第 3 轮一边打分一边先发下一个请求（显卡不闲着）：停下的时候那个请求已经发出去了，要么白做、要么让「试了几个」超过停下时的个数，
  停下的规则就不准了；一般的显卡第 1 轮就有 48 个、加第 2 轮正好 64 个，第 3 轮只在小显存 / 没有 N 卡时才用到。
- 留下来的存去掉首尾以后的声音：重新排名时要在两边补 0 再打分，和当时的分数对不上，「重新生成时最好的不会变差」就保证不了。
- 每次生成都用不带声纹的方式重建参考录音库：会把 P8 建的库里的声纹记录（自己的分数、音色变化）丢掉。
