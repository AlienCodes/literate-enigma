## pipeline#2 同一个视频一次准备里切了两遍

- **问题**：网页上传了「第1课.mp4」，旁边又填了它所在的文件夹（两个框并排）；或者文件夹里有「备份/第1课.mp4」「第1课 - 副本.mp4」。
  同一次准备里每一份都切一遍：30 段变 57~60 段，同一句话训练两次，还可能一份当训练、一份当考试（挑最像的模型时作弊）。
- **原因**：「处理过没有」在开始处理以前一次算完，同一次里先处理的那份记下以后，后面的副本不再比；找文件时只按路径去重。
- **怎么修**：新的 `prepare.pending_sources`：先跳过处理过的，再按内容（文件大小 + 开头结尾 1 MB 的指纹，不看文件名）
  分组，每组只留一份——有同名字幕的优先，再是文件夹里的原件（不是 uploads 里上传的），再不行就是先找到的。
  开始时的进度说明和结果提醒都写「另有 N 个和别的文件是同一个视频……只处理了一次，同一段话不会训练两次」。
  开始前的检查（`_precheck_prepare`，算硬盘空间、要不要语音识别）用同一个函数，副本也只算一份。
- **测试**：`test_same_video_uploaded_and_in_folder_is_cut_once`：上传 + 填文件夹 → 和只放一份一样多（30 段），用的是有字幕的那份；
  文件夹里有备份和「副本」→ 也是 30 段、`files_new == 1`。修以前 57 段。
- 没做：以前已经切了两遍的声音不会自动清理（要老师在校对表里删一份，或者新建声音）。

## pipeline#3 + synth#2 字幕不是 UTF-8（GBK / UTF-16）时素材丢掉；一段都没切出来也不说

- **问题**：记事本另存为 ANSI（中文 Windows 上是 GBK）的同名字幕，中文全变成「����」当成训练文字，被当成「疑似识别错误 /
  没有识别出文字」丢掉（30 段只剩 8 段英文）；「Unicode」（UTF-16）的字幕一条都读不出，这个视频 0 段，还记成处理过，
  以后再准备也不会重做。第③步上传的 .srt（按字幕时间生成）也一样读成乱码。整段静音、没录上声音的视频切出 0 段，什么都不说。
- **原因**：`parse_subtitles` 只按 UTF-8 读（读不了的字节换成「�」）；有同名字幕就完全信字幕、不再识别。
- **怎么修**：
  1. `textutil.decode_text_bytes`（从 `transcript_fix.read_text_file` 搬过来，两边共用）：BOM → UTF-32 / UTF-16（带不带 BOM）
     → 严格 UTF-8 → GB18030。UTF-8 的文件读出来和以前一模一样；UTF-8 文件里只坏了几个字节时照 UTF-8 读（不会整个当成 GBK
     读成乱码——这是修的时候发现的新坑，加了保护测试；英文字幕的情况复查时又修了一次，见「复查 synth#2」）。`parse_subtitles` 用它，第③步上传字幕也就跟着好了。
  2. 同名字幕读不出一条（不是字幕文件、坏了、一大半是乱码）：黑色窗口里说明原因，这个视频改用按停顿切 + 语音识别
     （`read_sidecar_cues`）。开始前的检查也知道这时要语音识别（`usable_sidecar`），没装识别组件会一开始就说。
     字幕文件一时打不开（被别的程序占着）照常报错：这个视频这次跳过，下次再试。
  3. 一段也没切出来的文件：结果里提醒「「第2课.wav」里没有找到能用的说话声音……请打开听一下，换成能听到你讲课声音的文件」。
     仍然记成处理过（真的静音的文件再处理一遍也没用；换了新文件，大小不同，会当新文件处理）。复查时补上：同名字幕换了
     会重新处理，以前的版本记下的 0 段也再处理一次（见「复查 pipeline#3」）。
- **测试**：`test_subtitles_saved_as_ansi_or_unicode_are_read`（gbk / utf-16 / 没有 BOM 的 utf-16-le 修以前失败，
  utf-8 / utf-8-sig 是保护）、`test_utf8_subtitle_with_one_broken_byte_is_still_read_as_utf8`（保护）、
  `test_gbk_sidecar_subtitle_keeps_all_material`（GBK 字幕切出来的文字、留下的条数和 UTF-8 一样）、
  `test_unreadable_sidecar_falls_back_to_silence_slicing`、`test_file_without_any_speech_is_reported`。
- 没做：以前已经被 GBK 乱码字幕坏掉、但还切出了片段的视频（切出 N 段、记成处理过）不会自动重做（片段和老师的修改都在校对表里，
  自动重切会冲掉老师改过的字；要重做就在校对表里删掉这些片段，或者新建声音）。一段都没切出来的（UTF-16 字幕）复查时已经能重做。

## pipeline#6 「有爆音」过滤永远不起作用

- **问题**：话筒太近、音量开太大录出来的破音，一条都查不出来，全拿去训练（手册说会去掉爆音）。
- **原因**：先把整段录音统一了音量（最响只有 -1 dB）再查有没有满格的样本，永远是 0。
- **怎么修**：`enhance_file` 在统一音量（和降噪、去背景音乐）以前，按原始录音每 1 毫秒数一次满格样本（`audio.clip_counts`，
  分块算；每毫秒 2 个字节，两小时的录音约 14 MB）；切片时每段记下 `clip_src`（这一段满格样本的比例），过滤按 `clip_src` 和旧的
  `clip_ratio` 里大的那个，门槛还是 0.2%。保存校对表时 `clip_src` 不会被冲掉。有爆音被去掉时结果里说明原因和怎么办
  （以后录音音量小一点、话筒远一点；听着没问题的句子可以点「✅ 这一条也要用」）。以前准备好的素材没有 `clip_src`，不受影响
  （确认过的素材不会变）。
- **量的结果**（`clipping_filter_结果.txt`）：放大 2 倍（整段 0.02% 满格）一条不丢；放大 2.5 倍（2.3%）起 10 条全是「有爆音」；
  修以前 6 倍（16.6% 满格）也一条不丢。
- **测试**：`test_clipped_recording_is_dropped_as_clipping`（约 5% 削顶 → 至少 8 成是「有爆音」；保存校对表以后还在）。

## pipeline#7 自动降噪把老师的声音削掉一块

- **问题**：「降噪：自动」（默认）在估计信噪比低于 25 dB 时降噪；讲课录音开头多半就在说话，降噪以后说话声反而少了 6~7 dB，
  比不降噪还差（削掉音色）。
- **原因**：调用 noisereduce 时没给噪声样本，它拿录音开头 600000 个样本（44.1 kHz 下 13.6 秒）当「噪声」，正好是说话声。
- **怎么修**：`enhance.noise_sample`：噪声样本取停顿里最安静的部分（连续 80 毫秒以上、两头各让出 20 毫秒，数字静音不算，
  最多 10 秒），作为 `y_noise` 交给 noisereduce（2.0.1 和 3.x 参数一样，和生成时的 `denoise_light` 同一个思路）。
  找不到 1 秒以上的停顿就不降噪、写一句原因（宁可不降，也不伤音色）。逐帧电平只算一次（以前估计信噪比时已经算过）。
- **量的结果**（`denoise_profile_结果.txt`，44.1 kHz）：说话声能量变化 修以前 -6.95 / -6.82 dB，现在 -1.00 / -1.49 dB，
  和直接给真正噪声样本的理想情况（-1.00 / -1.52 dB）一样。
- **测试**：`test_denoise_takes_its_noise_sample_from_pauses`（假的 noisereduce：收到的噪声样本 ≥ 1 秒、只有底噪）、
  `test_denoise_does_not_cut_the_voice_of_a_lecture_that_starts_with_speech`（真的 noisereduce，只有整合包环境有：
  修以前 -6.8 dB，现在不超过 3 dB）。

## pipeline#8 先记「处理过」、后写校对表：写校对表失败时这个视频永远丢了

- **问题**：写校对表（manifest）失败（硬盘满了、被同步 / 杀毒软件占着超过 3 秒、断电在两次写之间）：sources.json 已经记了
  「处理过」，再点准备素材时这个视频被跳过，它的片段永远不在校对表里，只说「没有找到新的视频」。
- **原因**：每个视频做完时先写 sources.json、后写 manifest。
- **怎么修**：
  1. 换过来：先写校对表，再记「处理过」。
  2. 校对表里已经有这个位置的视频的片段、sources.json 却没记（写完校对表就断电）：算处理过（不再切一遍，老师改过的字不会被冲掉），
     并补记进 sources.json（带内容指纹，以后搬家、改名也认得出）。
  3. 修以前的版本已经留下的：sources.json 记了「切出 N 段」（N > 0）、校对表里一段都没有 → 不算处理过，再准备一次就补上。
     片段编号由视频编号 + 顺序决定，重新切出来的编号一样。
- **测试**：`test_failed_manifest_write_does_not_lose_a_video`（第 2 个视频写校对表时出错，再准备一次两个视频都在）、
  `test_sources_record_and_manifest_out_of_step_are_repaired`（两种对不上的情况）。

## pipeline#9 去背景音乐（Demucs）时点「停止」不停；每个视频留下一个和视频一样长的人声文件

- **问题**：勾了「视频有背景音乐」，一两个小时的视频 Demucs 要二三十分钟，点「停止」要等它做完；每个视频都在 raw/ 里留下
  `.src.vocals.wav`（两小时约 1 GB）；Demucs 出错时 `demucs_*` 临时文件夹也留着。
- **原因**：Demucs 用一直等到结束的方式运行，不看停止按钮；用完的人声文件、出错时的临时文件夹没人删。

  人声文件读进来就删；准备素材每个视频做完（或出错、停止）时再删一遍，没做完时清理了一半的那份也删掉。

## pipeline#11 按停顿切时把很长的停顿切进一段

- **问题**（只影响没有字幕的视频）：老师说「好。」（1 秒），写板书 7 秒，再说一句：切成一段 11 秒、中间 7 秒底噪的训练片段，
  模型会学到句子中间长时间停顿。最后一句后面停很久再说「好。」也一样（检查时发现的第二处）。
- **原因**：当前这段不到 3 秒时，不管中间停多久都和下一段合并（只要不超过 12 秒）；「太短的尾巴并入前一段」也不看停顿。
- **怎么修**：`find_segments` 加 `max_merge_gap = 1.2` 秒（和生成时「异常停顿」的门槛一样），两处合并都不跨过更长的停顿；
  太短的那段自己成一段（不到 2 秒的以后算「太短」）。没有用 1.0 秒：原来测试里 1.0 秒的停顿量出来可能略长，会被切开。
- **以前准备好的素材不变**：处理过的视频不会再切，片段编号（视频编号 + 顺序）一条都不变。
- **测试**：`test_slicer_never_glues_a_short_phrase_across_a_long_pause`（两种情况：片段里没有超过 1.2 秒的停顿、都不到 8 秒）、
  `test_slicer_change_keeps_ids_of_prepared_material`（保护：再准备一次，编号、起止时间不变）。原来的切片测试照样通过。

### 复查 pipeline#3 一段也没切出来的视频永远不再处理（改名字也没用了）

- **复现**（gsv39）：「第1课.wav」配上另一个视频的字幕（时间都在 01:00 以后）→ 0 段、提醒「没有找到能用的说话声音」；
  把字幕换成对的再准备：`files_new 0`、还是 0 段，结果里没有任何原因（校对表是空的，连「这次没有找到新的视频」都不说）。
  pipeline#4 修好以后改了名字也认得出来，以前「改个名字」这条路也没了。修以前的版本读不了 UTF-16 字幕留下的
  `segments: 0` 记录也一样：现在的代码再准备还是 0 段。
- **原因**：`already_done` 把「处理过、切出 0 段」的记录一律当成处理过。
- **怎么修**（检查意见的方案 A）：
  1. 每个视频处理完记下同名字幕的指纹（`sources.json` 里的 `sub`：字幕的大小 + 开头结尾的指纹，不看名字；没有字幕是 `none`）。
  2. 「切出 0 段」的记录只有字幕指纹和现在一样才算处理过：换了字幕、加上或删掉字幕 → 重新处理；以前的版本记的（没有 `sub`，
     例如 UTF-16 字幕读不出的那些）→ 再处理一次（真的静音的文件会再提醒一次，以后就记上指纹了）。
     校对表里有片段的、切出 N 段（N > 0）的记录照旧，不会再切一遍。

### 复查 synth#2 英文字幕坏了一个字节，整个读成 GBK 乱码（还吃掉字母）

- **复现**：UTF-8 的英文字幕（we’ll、It’s、don’t、Let’s），第一个 ’ 少了最后一个字节 → 读出「we鈥ll」「It鈥檚」「don鈥檛」
  「Let鈥檚」：英文训练文字里冒出汉字，s、t 被吃掉；没有「�」，`read_sidecar_cues` 也照单全收。8a19206 以前的代码只坏「we�ll」一个字。
  母本 txt 没有变差（以前的 `read_text_file` 本来就会退到 GB18030）。
- **原因**：判断「只坏了几个字节」用的是「读坏的 ≤ 不是 ASCII 的字的 5%」。英文里不是 ASCII 的只有几个弯引号，坏一个就占两三成。
- **怎么修**：再加一条：读坏的 × 2 ≤ 按 UTF-8 读对了的三字节字（汉字、中文标点、弯引号）也照 UTF-8 读。只数三字节字，是因为
  GBK 的文字照 UTF-8 读时常常凑出合法的两字节字（ģ、Ͱ 之类），三字节的少得多。
- **实测**（`g4_脚本/decode_rule.py`，结果 `decode_rule_结果.txt`；材料是复查时仓库里的中文：教学手册、快速上手、程序里带汉字的
  5840 行，程序改了数字会略有变化）：
  - 存成 GBK，按 1/2/3/5/10/30 行一段试了 74606 段：现在用的判断读错 0 段（和第一次修的一样）；检查意见建议的「读坏的 <
    0.5 × 所有读对的字」读错 8 段（都是含 `add("GPT-SoVITS 模型版本", …)` 那一行的 1~2 行小段：一行英文里只有四个汉字，
    GBK 的「模型版本」8 个字节照 UTF-8 读，凑出「ģ」「Ͱ」「汾」3 个合法的字、只坏 1 个），所以没用它，改成只数三字节字（这一段只有「汾」1 个，不够坏的 2 倍）。
  - 英文字幕有 k 个弯引号、第一个坏了一个字节（去掉最后 / 中间 / 第一个字节）：现在 k ≥ 3 时都只坏 1 个字（第一次修的 k = 3/4/6
    时坏 5/7/11 个字）。k = 2 时三种判断都还是坏 3 个字：读对的三字节字只有 1 个，分不清是坏了的 UTF-8 还是 GBK，
    宁可这样，也不冒把 GBK 的母本、字幕整个读成乱码的险（坏的地方最多就是那两个弯引号附近）。
  - 中文 UTF-8 30 行一段坏 1~3 个字节：9000 段都照 UTF-8 读。
- **母本**：母本 txt（`transcript_fix.read_text_file`）用的是同一个函数。GBK / UTF-16 / UTF-8 的母本读法不变；UTF-8 的母本
  坏了几个字节时照 UTF-8 读（只坏那几个字），不会整个读成乱码，查错字、文字校正还是以母本为准。
- **测试**：`test_english_utf8_subtitle_with_one_broken_byte_stays_english`（上面复现的字幕：没有汉字，后两条和原文一样，
  第一条只坏 ’ 那一个字）。原来的保护测试（GBK、UTF-16、中文 UTF-8 坏一个字节）照样通过。
