# 出片搬到 GitHub 机器（用户 2026-10-17：“那肯定要做这个方案……我们的方法要按照虹吸效应不停的去升级”）

## 起因
别的会话第 5 篇因容器空闲被回收连丢两次。我们这边配音模型、配音缓存、工作目录（约 3.3 GB）也只在容器里，没进 GitHub；
配音缓存是之前所有核实过的停顿、切点、确认绑定的“第一次合成”，丢了换机器重合成可能差一点点，确认就全部作废。
我的疏漏：升级一直只做局部小程序，没处理这个结构性风险。以后每篇的方法复盘都要问一句“哪些东西只在容器里”。

## 方法设计（T31）
- 步骤：① 缓存钥匙改成可移植（模型内容校验码，不含路径、修改时间），跑 01–20 篇出声音 + 出片前核查，记下真正用到的缓存并搬到新钥匙 →
  ② 用到的缓存、声音配方、固定版本清单、安装脚本存进仓库（模型写下载地址和校验码）→
  ③ literate-enigma 加 GitHub 自动任务（篇目清单 → 每篇一台机器 → 出片 + 全部核查 → 通过才保存）→
  ④ 证明：GitHub 上重出第16篇，定稿视频核对必须与存档逐屏、逐采样一致 → ⑤ 以后定稿、批量出片交给它
- 每步谁做：①② 程序跑，我只看结论；③ 我写一次；④ GitHub 跑，我看结论
- 预计调用：10–14 次；预计 token：本会话约 600 万等效（会话长、每次重读量大）
- 为什么有效：定稿视频核对已能逐屏、逐采样比对；只要缓存带过去、软件版本固定，GitHub 出的片就与这里一致；不一致就停
- 开工时刻：2026-10-17T05:45（UTC）

- 修隐患：GitHub 默认 shell 没有 pipefail，`make_video … | tail` 出错会被盖住、照样显示通过；改成 `shell: bash`（带 pipefail），没出片就上传失败。
- 下一步检验：清单“16 声音重合成”——GitHub 机器清空缓存从头合成，看与存档是否逐采样相同。相同，则新篇的配音也能交给 GitHub；不同，则新句子仍在一处合成、以缓存为准。
- 检验结果（run 39044302941）：GitHub 机器清空缓存从头合成 16，出片程序自己的守门 A21 停下：“供体的合成变了：Bring a pipe, and then they left.”
  → 换一种 CPU，合成的声音就不逐采样相同（本容器 CPU：Intel(R) Xeon(R) Processor @ 2.10GHz）。同一种机器上从头合成是确定的（本地已证）。
  结论：新句子只在一处（本容器这类机器）合成，缓存就是唯一的原版；GitHub 机器只用缓存拼装，再与存档比对。
- 补漏：出片程序每用到一条缓存就自动复制进 `视频/配音缓存/`（`_to_repo`，严格模式不复制），推送两仓库时一起进 GitHub。
  核查程序是 exec 出片程序的代码来合成的，也走同一个缓存，以后跑核查时自动收进仓库。试过：删掉一条再出声音，自动复制回来、内容相同。
- 已知限制：独立复核（`独立复核/synth.py`）故意不用缓存、重新合成逐样本比对，所以交付核查只能在合成一致的同类机器上跑；GitHub 只做出片 + 与存档比对。
