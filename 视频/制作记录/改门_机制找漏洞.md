## 方法设计（虹吸：程序找，人只看程序列出的少数几处）
A. **门变异演练（全自动找漏洞，主体）**：新程序 `门变异.py`。
   1. 自动列出所有“停”的点：定稿流水线.sh、草稿声音.sh 等正式入口 .sh 里每个 `stop`、`|| {`、`exit 非0`；交付核查.py、踩坑核查.py 等正式入口里每个把结论变成“不通过/停”的分支（按 AST 或标记找，不手写清单；新加的门自动进来）。
   2. 在临时副本里一次拆一个（删掉/改成恒通过），跑对应的流程自检、执行效应演练的相关场景。
   3. 拆了没有任何东西发现 = 漏洞，列出来（文件:行、这道门挡什么）。每个漏洞补一个演练场景或自检，补完重跑必须发现。
   4. `门变异缺口基线.json` 只许减少，目标 0；规则执行核查查基线（变多就停）。全量变异很慢 → 写成 GitHub 请求（drill.yml，推请求.py + send_later，G74），改了门程序的推送和每天一次跑；沙盒只跑改动文件涉及的那几道门。
   5. 先小规模证明有效：只对 定稿流水线.sh 的 26 个 stop 跑，K37 原样那一行（`|| stop` 在注释里）必须被列为漏洞，修好后不再列。
B. **每篇“## 机制漏洞”记录（28 起）**：NN.md 必须有这一节。程序（收工记录.py 或 开工记录.py）按本篇时间窗口从 坑登记.json 自动填本篇登记的 K#、门停了查出是程序毛病的次数、手工绕过的地方；会话补“这次机制哪里没挡住/哪里不顺”，没有写“无”并附依据。踩坑核查 没有这一节就停（同 T29 的做法，带自检）。
C. **漏洞趋势进方法进化表**：方法进化表.md 每篇加一列“机制漏洞数（K#，程序毛病/内容问题）”；比前三篇中位数变差，沿用 G65：方法复盘必须写查得到的“进化落地：<提交号|G##|K##>”，没有就停。
D. **CLAUDE.md 加一条（第20条）**：用户原话 + 门（A 的变异基线、B 的踩坑核查、C 的进化表），和门、自检、演练同一次推送（否则规则执行核查报缺口）。
